다섯 단계를 한눈에:

**표 3. 에이전트 설계 5단계 개요**

| 단계 | 이름 | 하는 일 | 다루는 절 |
|:---:|---|---|:---:|
| 1 | 분해 | 업무를 개별 스텝(노드 후보)으로 쪼갠다 | §2 |
| 2 | 스텝 유형 식별 | 각 노드가 어떤 종류의 작업인지 분류한다 | §2 |
| 3 | State 설계 | 노드 간 공유 메모리의 스키마를 정의한다 | §3 |
| 4 | 노드 구현 | 각 스텝을 함수로 구현(에러·개입 포함) | §3·§4 |
| 5 | 연결 | 노드를 그래프로 잇고 컴파일한다 | §4 |

### 2.1. Step 1 — 워크플로우를 개별 스텝으로 분해

먼저 업무 안의 서로 다른 단계를 식별한다. 각 단계가 하나의 **노드**(한 가지 일만 하는 함수)가 된다. 그런 다음 이 단계들이 어떻게 이어지는지 스케치한다.

![트레이딩 에이전트 그래프](figs/fig03_trading_agent_graph.svg)
<small>Figure — 평균회귀 트레이딩 에이전트 그래프. **실선** 은 늘 같은 다음 노드로 가는 고정 엣지, **보라 점선** 은 노드 내부에서 `Command(goto=...)` 로 결정하는 분기다. (`approve_order` 가 두 번 보이는 것은 같은 노드를 두 진입 경로 — 리스크 차단 에스컬레이션, 정상 사이징 후 검토 — 로 나눠 그린 레이아웃 단순화다.)</small>

화살표는 **가능한 경로** 를 보여줄 뿐, 실제로 어느 길로 갈지의 결정은 각 노드 **안에서** 일어난다(점선이 분기 가능 경로다).

각 노드가 할 일:

**표 4. 트레이딩 에이전트의 노드별 역할**

| 노드 | 하는 일 |
|---|---|
| `fetch_market_data` | 최근 종가(또는 스프레드) 윈도우를 가져온다 |
| `generate_signal` | z-score 로 방향·확신을 정하고 다음 행동으로 라우팅 |
| `check_risk` | 변동성·노출을 점검하고 허용 한도를 계산 |
| `flag_anomaly` | 데이터 품질 이상을 기록(무거래) |
| `size_position` | 한도 안에서 고정비중 주문 수량을 산출 |
| `approve_order` | 사람에게 주문 승인/거부/수정 에스컬레이션 |
| `place_order` | 브로커로 주문 전송 |

> **유의**: 어떤 노드는 다음 행선지를 **스스로 결정** 하고(`generate_signal`, `check_risk`, `approve_order`), 어떤 노드는 늘 같은 다음 노드로 간다(`fetch_market_data` → 항상 `generate_signal`). 이 차이가 §4 에서 "엣지는 최소, 라우팅은 노드 안" 으로 이어진다.

### 2.2. Step 2 — 각 스텝이 무엇을 하는지(유형) 식별

분해한 각 노드가 어떤 **종류** 의 작업이고, 제대로 동작하려면 어떤 맥락이 필요한지 정한다. 작업은 대체로 네 유형으로 나뉜다.

**표 5. 네 가지 스텝 유형**

| 유형 | 언제 쓰나 | 예 |
|---|---|---|
| 🧠 **LLM 스텝** | 이해·분석·생성·추론 판단이 필요할 때 | `generate_signal`(근거 생성) |
| 🗄️ **데이터 스텝** | 외부 소스에서 정보를 가져올 때 | `fetch_market_data`, `check_risk` |
| ⚡ **액션 스텝** | 외부에 실제 행동을 가할 때 | `place_order`, `flag_anomaly` |
| 👤 **사용자 입력 스텝** | 사람의 개입이 필요할 때 | `approve_order` |

![네 가지 스텝 유형](figs/fig04_step_types.svg)
<small>Figure — 네 가지 스텝 유형과 트레이딩 에이전트에서의 예시 노드. (`size_position` 처럼 순수 계산만 하는 노드는 LLM 스텝의 결정론적 변형으로 본다.)</small>

각 유형마다 고려할 점이 다르다.[^1]

- **LLM 스텝**은 *정적 맥락(프롬프트)* 과 *동적 맥락(State 에서 오는 데이터)*, 그리고 *원하는 출력 형태* 를 구분해 둔다. 예컨대 `generate_signal` 의 정적 맥락은 "평균회귀 해석 규칙·출력 포맷", 동적 맥락은 "가격 윈도우·헤드라인" 이다. (방향 자체는 결정론적 z-score 가 정하고, LLM 은 근거·구조화 출력을 맡는다 — §3.2.)
- **데이터 스텝**은 *파라미터·재시도 전략·캐싱* 을 따진다. 시세 조회는 일시적 실패에 지수 백오프 재시도를 걸 만하고, 자주 쓰는 질의는 캐시할 수 있다.
- **액션 스텝**은 *언제 실행할지·재시도 전략* 을 정하되 **캐시하지 않는다** — 매 주문 전송은 고유한 행동이다.
- **사용자 입력 스텝**은 *판단에 필요한 맥락·기대 입력 형식·언제 트리거되는지* 를 정한다.

이렇게 스텝 유형을 먼저 분류해 두면, 같은 "노드" 라도 재시도·캐싱·에러 처리 정책을 유형별로 다르게 가져갈 근거가 생긴다(§3 의 에러 표로 이어진다).
