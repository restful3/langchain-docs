### 1.1. 한 번의 LLM 호출로는 부족한 순간

간단한 질문 하나라면 LLM 을 한 번 부르면 끝이다. 그러나 현실의 에이전트 업무는 그렇지 않다. 예컨대 "종목 시세를 읽고, 평균회귀 신호로 방향을 판단하고, 리스크 한도를 점검하고, 주문 전에 사람 승인을 받고, 체결을 기록하라" 같은 업무는 **여러 단계 · 분기 · 외부 호출 · 사람 개입** 이 얽힌다.

이런 업무를 함수 하나에 if/for 로 몰아넣으면, 중간에 무슨 일이 일어났는지 들여다볼 수 없고, 한 단계가 실패하면 처음부터 다시 해야 하며, "사람의 승인을 기다리는 동안 멈춰 있기" 같은 동작을 표현하기 어렵다.

### 1.2. 세 가지 부품

LangGraph 는 이 복잡함을 세 가지 부품으로 분해한다.

**표 2. LangGraph 의 세 부품**

| 부품 | 역할 | 비유 |
|---|---|---|
| **노드(Node)** | 한 가지 일을 하는 함수. State 를 받아 업데이트를 돌려준다 | 작업대 위의 한 공정 |
| **엣지(Edge)** | 한 노드 다음에 어느 노드로 갈지 | 공정 사이의 컨베이어 |
| **상태(State)** | 모든 노드가 공유하는 메모리. 노드는 여기서 읽고 여기에 쓴다 | 작업 노트 |

![노드·엣지·State 세 부품](figs/fig01_three_parts.svg)
<small>Figure — 노드는 작업(state→update)을 하고, 엣지는 다음 노드를 가리키며, State 는 모든 노드가 읽고 쓰는 공유 메모리다.</small>

> 공식 문서의 표현을 빌리면, **"노드는 작업을 수행하고, 엣지는 다음에 무엇을 할지 알려줍니다."**[^1] 로직(노드)과 제어 흐름(엣지)을 분리하는 것이 LangGraph 의 기본 철학이다.

### 1.3. 그래프로 쪼개면 무엇을 얻나

업무를 여러 노드로 잘게 쪼개는 데는 비용이 따른다 — 코드가 함수 하나보다 길어진다. 그럼에도 그렇게 하는 이유는 세 가지 이득 때문이다.[^1]

- **스트리밍 진행상황**: 노드 경계마다 "지금 어디까지 했다" 를 사용자에게 흘려보낼 수 있다.
- **내구성 있는 일시정지·재개**: 노드 경계에서 상태를 저장해 두므로, 멈췄다가 며칠 뒤에 이어서 실행할 수 있다.
- **단계별 디버깅**: 노드 사이에서 State 를 들여다보며 "신호 생성기가 무엇으로(z-score·방향) 판단했는지" 를 주문 전에 확인할 수 있다.

### 1.4. 따라갈 예제 — 평균회귀 트레이딩 에이전트

앞으로 §4 까지 함께 따라갈 예제다. 공식 문서가 고객지원 에이전트로 보여 준 **설계 흐름** 을, 이 발제에서는 퀀트 사례로 옮겼다.[^1] 요구 동작은 이렇다.

```text
에이전트는 다음을 해야 한다:
- 종목의 최근 시세(종가 윈도우)를 가져온다
- z-score 로 평균회귀 방향·확신을 판단한다
- 진입 신호면 변동성·노출 한도를 점검한다
- 한도 안에서 주문 수량을 산출한다
- 주문 전송 전 사람의 승인을 받는다
- 데이터 이상이면 기록하고 거래하지 않는다

처리해야 할 시나리오:
1. 저평가 되돌림: 가격이 평균 아래로 크게 벗어남 → 롱
2. 급등 과열:     가격이 평균 위로 크게 벗어남 → 숏 (강한 신호 → 사람 검토)
3. 평탄:         평균 근처 → 무거래
4. 변동성 초과:   리스크 한도 초과 → 사람 에스컬레이션
5. 데이터 이상:   결측·비정상 가격 → 이상 기록, 무거래
```

> ⚠️ **교육용 예제다.** 실제 매매 전략이 아니라 LangGraph 의 노드·엣지·State 를 보여 주기 위한 dry-run 이다 — 신호·리스크·사이징은 의도적으로 단순화했다.

이 업무를 LangGraph 로 옮기는 일은 보통 **다섯 단계** 를 거친다. §2 부터가 그 다섯 단계다.
