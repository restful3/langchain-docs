### 1. 그림 2 / `fig02_email_agent_graph.svg` 55~57, 본문 112~116

**문제**  
본문 캡션은 "실선은 늘 같은 다음 노드로 가는 고정 엣지, 보라 점선은 노드 내부 `Command(goto=...)` 분기"라고 설명합니다. 그런데 그림에서는 `human_review` 에서 `draft_response` 로 가는 선이 실선입니다. 원문 06의 Mermaid 도 `human_review1 --> draft` 로 실선이라 출처와는 일치하지만, §2.1 본문 134줄과 §4.2 본문 426줄은 `human_review` 도 다음 행선지를 스스로 결정하는 노드라고 설명합니다. 같은 이름의 `human_review` 가 "분류 직후 에스컬레이션 후 draft 로 돌아오는 검토"와 "draft 이후 승인/거절 라우팅" 두 역할로 보이기 때문에, 실선/점선 의미가 초심자에게 약간 흔들립니다.

**권장 수정**  
그림 자체를 크게 바꿀 필요는 없습니다. 캡션이나 본문에 "도식의 첫 번째 `human_review` 는 검토/보강 후 draft 로 이어지는 고정 경로를 단순화해 그린 것이고, 아래쪽 `human_review` 는 승인/거절 라우팅을 나타낸다"는 한 문장을 추가하면 충분합니다. 또는 첫 번째 노드를 `escalation_review` 처럼 라벨링해 두 `human_review` 의 역할을 분리하세요.

### 2. 그림 7 / `fig07_interrupt_resume.svg` 22~29, 본문 468~472

**문제**  
그림은 `checkpointer` 박스에서 바로 `Command(resume=)` 박스로 화살표가 이어져 있어, checkpointer 가 resume 명령을 만든다는 인상을 줄 수 있습니다. 실제 흐름은 외부 호출자가 같은 `thread_id` config 와 함께 `app.invoke(Command(resume=...), config)` 를 호출하고, 그래프 런타임이 checkpointer 에서 저장된 checkpoint 를 조회해 해당 `interrupt()` 호출이 resume 값을 반환하도록 재실행/재개하는 쪽에 가깝습니다. 본문 468줄의 설명은 정확하지만, 그림만 보면 주체가 조금 모호합니다.

**권장 수정**  
`Command(resume=)` 박스 라벨을 "외부 호출자: Command(resume=)" 또는 "resume invoke" 로 바꾸는 것을 권합니다. 화살표도 `checkpointer → Command(resume=)` 보다는 `Command(resume=) → checkpointer 조회 → 재개` 흐름이 더 정확합니다. 공간을 아끼려면 현재 구조를 유지하되 `Command(resume=)` 박스 하단 텍스트를 "같은 thread_id 로 호출" 정도로 바꾸면 오해가 줄어듭니다.

### 3. 그림 8 / `fig08_node_granularity.svg` 33~39, 본문 478~486

**문제**  
"작은 노드 여럿" 쪽에서 `search 실패 → search 만 재실행`, `체크포인트 보존`이라고 단정합니다. 교육적 요지는 맞지만, 기술적으로는 실패/interrupt 시점, checkpointer durability mode, side effect 위치, 재시도 정책 적용 여부에 따라 실제 재실행 범위는 "마지막 checkpoint 이후" 또는 "실패한 노드/슈퍼스텝"으로 설명하는 편이 더 안전합니다. 본문 482줄은 "노드/슈퍼스텝 경계"라고 완화했는데, 그림은 더 강하게 단정합니다.

**권장 수정**  
그림 라벨을 "search 부터 재실행" 또는 "대체로 search 재실행"으로 완화하세요. `체크포인트 보존`도 "이전 checkpoint" 정도가 더 정확합니다. 캡션도 "노드를 작게 쪼갤수록 실패 시 재실행 범위가 줄어든다"는 현재 표현은 좋지만, 그림 안의 "search 만"은 조금 낮추는 편이 좋습니다.

### 4. 그림 9 / `fig09_local_topology.svg` 14~19, 본문 504~510

**문제**  
그림은 `langgraph.json → langgraph dev` 화살표에 "등록"이라고 표시합니다. `langgraph.json` 이 그래프 경로와 assistant 이름을 등록하는 파일이라는 의미로는 맞지만, 실행 시점의 관계는 `langgraph dev` 가 `langgraph.json` 을 읽어 그래프를 로드한다는 쪽입니다. "등록"만 보면 `langgraph dev` 가 어딘가에 등록 작업을 수행하는 것으로 읽힐 여지가 있습니다.

**권장 수정**  
화살표 라벨을 "읽음", "로드", 또는 "graph 경로 로드"로 바꾸세요. 캡션의 "등록된 그래프를 ... 띄운다"는 표현은 적절합니다.

### 5. 전체 그림 / SVG 내부 설명 텍스트 규칙

**문제**  
프로젝트 규칙은 "SVG 본체에는 다이어그램만, 모든 설명 텍스트는 그림 밖 Markdown 캡션으로 분리"입니다. 현재 SVG들은 별도 제목이나 장문 범례 박스는 넣지 않아 큰 틀은 지키고 있습니다. 다만 `fig07` 의 "⏸ 며칠 뒤라도", `fig08` 의 "끝에서 실패 → 전부 재실행", "체크포인트 보존", `fig09` 의 "인메모리 · :2024 (개발용)" 같은 문구는 다이어그램 라벨과 설명 텍스트의 경계에 걸쳐 있습니다.

**권장 수정**  
규칙을 엄격히 적용한다면 SVG 내부는 객체명과 짧은 관계어만 남기고, 설명성 문장은 캡션으로 빼세요. 예: `fig07` 내부의 "며칠 뒤라도"는 캡션에 이미 들어갈 수 있고, `fig08` 의 "큰 노드는 끝에서 실패해도..."는 본문 캡션에 이미 있습니다. 다만 현재 수준은 학습용 다이어그램 라벨로 볼 수도 있어 필수 수정은 아닙니다.

### 6. 그림 1 / `fig01_three_parts.svg` 28~34

**문제**  
State 와 노드의 관계를 `노드① → State` 는 쓰기, `State → 노드②` 는 읽기로만 보여 줍니다. 캡션과 본문은 "모든 노드가 읽고 쓴다"라고 하므로 개념적으로는 양방향 관계입니다. 그림은 단순화를 위해 한쪽씩만 그린 것으로 보이지만, 처음 보는 독자에게 "한 노드는 쓰고 다른 노드는 읽기만 한다"는 인상을 줄 수 있습니다.

**권장 수정**  
선 두 개를 모두 양방향으로 만들 필요는 없습니다. 캡션이 이미 보완하고 있으므로 선택 사항입니다. 더 명확히 하려면 각 노드에서 State 로 내려가는/올라가는 얇은 양방향 화살표를 쓰거나, 라벨을 "읽기/쓰기"로 통합하세요.

### 7. 그림 번호 배치 / 본문 104~114

**문제**  
본문에서는 그림 3이 그림 2보다 먼저 나옵니다. 의도상 5단계 전체를 먼저 보여 주고 Step 1의 그래프를 뒤에 배치한 것으로 보이며 학습 흐름은 자연스럽습니다. 다만 "그림 번호"만 기준으로 읽는 독자나 PDF 목차/참조에서는 번호가 역전되어 보일 수 있습니다.

**권장 수정**  
번호 순서를 문서 등장 순서와 맞추려면 현재 그림 3을 그림 2로, 이메일 에이전트 그래프를 그림 3으로 바꾸세요. 기존 번호가 원고 설계상 의미가 있다면 유지해도 치명적 문제는 아닙니다.

## 전반 평가

9개 SVG는 전반적으로 본문 핵심 개념을 잘 시각화합니다. 특히 그림 2의 실선/점선 구분, 그림 6의 에러 유형·주체·전략 매핑, 그림 9의 `langgraph.json` 중심 로컬 서버 토폴로지는 발표 보조자료로 효과적입니다. 기술적으로 큰 오류는 없고, 대부분의 보완점은 그림이 교육적 단순화를 위해 주체나 조건을 압축하면서 생기는 작은 오해 가능성입니다. 우선순위는 그림 7의 resume 주체 표현, 그림 8의 "search 만 재실행" 단정 완화, 그림 9의 "등록" 라벨 수정입니다. 이 세 가지만 정리하면 시각 자료의 정확성과 본문 정합성은 충분히 안정적입니다.
